# データ品質ってどう評価するの？

データエンジニアリングの世界において、「データ品質」は避けて通れない重要なテーマです。どんなに高度な機械学習モデルや見栄えの良いダッシュボードを作っても、入力されるデータが「ゴミ」であれば、出力される結果も「ゴミ」になってしまいます。この原則を Garbage In, Garbage Out (GIGO) といいます。

オライリーの『[データエンジニアリングの基礎](https://www.oreilly.co.jp/books/9784814400652/)』では、データ品質の特性として主に以下の3つが挙げられています。

> - 正確性: 収集したデータは事実として正しいか？重複した数字はないか？数値は正確か？
> - 完全性: レコードは完全か？すべての必須項目に有効な値が得られているか？
> - 適時性: レコードは期限内に得られたか？

この3つの分類は網羅性があり、非常に美しい洞察です。しかし、実際のデータエンジニアリングの現場では、これら抽象的な概念を**どのように具体的な評価指標に落とし込むか**が課題となります。

本記事では、この「正確性」「完全性」「適時性」の3つについて、データオブザーバビリティの先駆者である Monte Carlo や、データ変換ツールのデファクトである dbt Labs などが提唱するベストプラクティス（[Monte Carlo: Data Quality Metrics](https://www.montecarlodata.com/blog-data-quality-metrics/) / [dbt: Testing Data Quality](https://docs.getdbt.com/docs/build/tests)）を参考に、具体的な評価・監視方法をまとめます。

## 1. 正確性 (Accuracy)
「データは現実世界を正しく反映しているか？」を問う特性です。実は、基準となる Ground Truth が必要になるため、評価が最も難しい特性でもあります。

**評価のプラクティス:**
*   **ビジネスルールの制約 (Business Rule Constraints):** データに対する「常識的な範囲」や「許容される値」を定義し、それを逸脱していないかチェックします。dbt の組み込みテストである `accepted_values`（ステータスが "Active" か "Inactive" のみか等）や、SQLベースのカスタムテストがこれに該当します。
*   **システム間でのクロスチェック (Cross-System Validation / Referential Integrity):** データウェアハウス（DWH）の集計結果と、本番系のデータベースの値を比較します。また、dbt の `relationships` テストのように、子テーブルの外部キーが親テーブルに必ず存在するかという参照整合性の確認も正確性を担保する手法です。
*   **異常検知 (Anomaly Detection):** 統計的なプロファイリングを用いて、過去のパターンから大きく外れた外れ値（Outliers）を検知します。Monte Carlo のようなデータオブザーバビリティツールは、機械学習を用いて「平均決済額の急激な低下」などを自動で検知するアプローチをとっています。

**代表的な指標 (Key Metric):**
*   `正確性レート = (全レコード数 - エラーのあるレコード数) / 全レコード数`

## 2. 完全性 (Completeness)
「必要な情報が欠落せずに揃っているか？」を問う特性です。データがその目的のために十分に使える状態であることを保証します。

**評価のプラクティス:**
*   **Null / 空値のチェック (Null/Empty Checks):** 必須項目（例：`user_id` や `transaction_date` など）における Null 値の割合を監視します。dbt では `not_null` テストとして最も頻繁に利用される基本プラクティスです。
*   **レコード数の照合 (Row Count Reconciliation):** ソースシステムから抽出（Extract）されたレコード数と、ターゲットシステムへロード（Load）されたレコード数が一致しているか（Volume checks）を比較します。
*   **スキーマドリフトの監視 (Schema Drift Monitoring):** データソース側で新しいカラムが追加されたり、既存のカラムが削除されたりする変更を検知します。これに気づかないと、一部のデータが欠落したままパイプラインが動いてしまう可能性があります。

**代表的な指標 (Key Metric):**
*   `完全性スコア = Nullではない有効な値の数 / 期待される全値の数`

## 3. 適時性 (Timeliness / Freshness)
「必要なタイミングでデータが利用可能になっているか？」を問う特性です。イベントが発生してから、DWHなどでデータが消費可能になるまでの遅延（レイテンシ）を測定します。

**評価のプラクティス:**
*   **データの鮮度監視 (Data Freshness):** dbt では `src/sources.yml` に `freshness` ブロックを定義し、`warn_after` や `error_after` を設定することで、データが許容される時間以上古い場合に警告を出すプラクティスが標準的に組み込まれています。
*   **SLA遵守の監視 (SLA Compliance):** 「日次レポート用のデータは朝8時までに準備完了していること」といったSLA（サービスレベル合意）を満たしている割合を測定します。
*   **遅延のトラッキング (Latency Tracking):** イベントが発生した時刻（`event_timestamp`）と、システムに取り込まれて処理が完了した時刻（`processed_timestamp`）の差分を計算し、パイプラインのボトルネックを監視します。

**代表的な指標 (Key Metric):**
*   `データレイテンシ = 処理完了時刻 - イベント発生時刻`

## データ品質を担保するためのベストプラクティス

これらの特性を評価するためには、場当たり的な対応ではなく、データパイプライン全体での仕組みづくりが求められます。

1.  **シフトレフト (Shift Left):**
    データ品質のチェックは、パイプラインのできるだけ早い段階で実施します。Great Expectations を用いた「データコントラクト（取り込み時のバリデーション）」や、dbt Cloud による CI/CD 時のテスト自動実行など、「ゴミ」が下流に流れ込む前に水際で防ぐ（[Shift-Left Data Quality](https://greatexpectations.io/)）アプローチが主流です。
2.  **ツールによる自動化:**
    **Great Expectations**、**dbt tests**、**Deequ** といったデータ品質評価フレームワークを利用し、データオーケストレーション（Airflow, Dagsterなど）の一部としてテストを自動実行します。
3.  **閾値と対応レベルの定義:**
    すべてのエラーでパイプラインを停止させる必要はありません。ビジネスへの影響度に応じて、「警告（ログ出力やアラート通知のみ）」と「失敗（パイプラインを停止）」の閾値を明確に定義します。
4.  **データオブザーバビリティ (Data Observability):**
    [Monte Carlo](https://www.montecarlodata.com/) などが提唱するように、データ品質の指標を継続的に監視し、機械学習を活用して「未知の未知（Unknown Unknowns）」である品質低下のトレンドをいち早く察知する体制を作ります。

## まとめ

オライリーの『データエンジニアリングの基礎』で語られる「正確性」「完全性」「適時性」は、データ品質を考える上での強力な羅針盤となります。これらを抽象的な概念のまま終わらせず、dbt や Monte Carlo、Great Expectations といったモダンなデータスタックのベストプラクティスを参考に、具体的なテストや監視に落とし込んでいくことが、データエンジニアの重要な腕の見せ所と言えるでしょう。
