> ※この記事はデータ品質シリーズの1本です。前回は「データ品質の全体像」を扱いました。今回はその中でも最も身近で、しかし奥が深い「完全性（Completeness）」を掘り下げます。

## はじめに

「データが揃っている」とは、どういう状態を指すのでしょうか。

`NULL` が無ければ完全なのか。行数が想定どおりなら完全なのか。実はこの「完全性（Completeness）」という言葉は、文脈によって指すものがまったく違います。曖昧なまま「完全性チェックを入れました」と言うと、後になって「肝心の欠損が検知できていなかった」という事故につながります。

この記事では、完全性を **3つのレベル** に分解して整理し、それぞれの測り方・SQLでの検知方法・よくある落とし穴・仕組みでの担保方法までを、実務目線でまとめます。

## そもそも「完全性」とは

データ品質のフレームワーク（DAMA-DMBOK など）では、完全性はおおむね次のように定義されます。

> **完全性（Completeness）**：必要とされるデータが、必要とされる範囲で存在しているか。

ポイントは「**必要とされる**」という部分です。完全性は「欠損がゼロ」という絶対値ではなく、**「業務上あるべき姿」に対してどれだけ埋まっているか** という相対的な尺度です。

たとえば「携帯電話番号」カラムが半分 `NULL` でも、その業務で携帯番号が任意項目なら完全性は問題ありません。逆に必須のはずの「メールアドレス」が1件でも欠けていれば、それは完全性の欠陥です。

つまり完全性を語るには、まず **「何が、どこまで揃っているべきか」という期待値（仕様）** が必要になります。ここが曖昧なプロジェクトでは、完全性チェックはほぼ機能しません。

## 完全性を3つのレベルに分解する

実務では、完全性を次の3レベルで考えると整理しやすいです。

| レベル | 問い | 欠損の単位 | 代表的なチェック |
| --- | --- | --- | --- |
| ① 属性（カラム）レベル | 「この項目、埋まってる？」 | セル（値） | `NULL` 率、空文字率 |
| ② レコード（行）レベル | 「あるべき行が全部ある？」 | 行 | 件数比較、キーの欠落 |
| ③ データセット（母集団）レベル | 「対象範囲を取りこぼしてない？」 | 期間・区分など | 期待母集団との突き合わせ |

以下、それぞれ見ていきます。

### ① 属性（カラム）レベルの完全性

もっとも馴染みがあるのがこれです。「必須項目に値が入っているか」。

```sql
-- users テーブルの必須項目の欠損率を確認する
SELECT
  COUNT(*)                                         AS total_rows,
  COUNT(*) - COUNT(email)                          AS email_nulls,
  ROUND(100.0 * (COUNT(*) - COUNT(email)) / COUNT(*), 2) AS email_null_pct
FROM users;
```

ただし、ここに**最初の落とし穴**があります。`NULL` だけを見ても不十分です。

- 空文字 `''`
- 半角スペースだけ `' '`
- `'N/A'`, `'null'`, `'-'`, `'unknown'` などの**擬似的な欠損値**

これらは `IS NOT NULL` を素通りしますが、業務的には「未入力」です。

```sql
-- NULL だけでなく「実質的な欠損」も欠損として数える
SELECT
  COUNT(*) AS total_rows,
  SUM(
    CASE
      WHEN email IS NULL
        OR TRIM(email) = ''
        OR LOWER(TRIM(email)) IN ('n/a', 'null', 'none', '-')
      THEN 1 ELSE 0
    END
  ) AS email_missing
FROM users;
```

> **観点**：完全性チェックを設計するときは、まず「このカラムにおける“欠損”の定義」をチームで合意すること。`NULL` = 欠損とは限らない。

### ② レコード（行）レベルの完全性

「値は埋まっているが、そもそも**行そのものが欠けている**」という欠損です。属性レベルよりも気づきにくく、事故になりやすいのがこのレベルです。

典型例：

- 日次で1万件来るはずの注文が、今日は8,000件しか無い
- マスタに存在するはずの店舗が、集計テーブルに現れない
- ETL の途中でパーティションが1つ丸ごと落ちた

**件数の相対比較**が基本の検知手段になります。

```sql
-- 直近7日と比較して、当日の件数が大きく減っていないか
WITH daily AS (
  SELECT order_date, COUNT(*) AS cnt
  FROM orders
  WHERE order_date >= CURRENT_DATE - INTERVAL '8 days'
  GROUP BY order_date
)
SELECT
  order_date,
  cnt,
  AVG(cnt) OVER (
    ORDER BY order_date
    ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING
  ) AS prev7_avg
FROM daily
ORDER BY order_date DESC;
```

また「参照先には存在するのに、こちらのテーブルには無い」＝**参照完全性の欠落**もこのレベルです。

```sql
-- マスタにあるが集計テーブルに現れない店舗（取りこぼし）
SELECT s.store_id
FROM store_master s
LEFT JOIN daily_sales d
  ON d.store_id = s.store_id
 AND d.sales_date = CURRENT_DATE - 1
WHERE s.is_active
  AND d.store_id IS NULL;
```

### ③ データセット（母集団）レベルの完全性

もっとも抽象度が高いのがこれです。「**そもそも対象範囲を取りこぼしていないか**」。

- 全国47都道府県のデータのはずが、46件しか無い
- 1時間ごとのログが、23個しか無い（1時間ぶん欠測）
- 「全店舗」と言いながら、新規開店した店が連携対象に入っていない

これは、**期待される母集団（マスタ・カレンダー・区分の一覧）と実データを突き合わせる**ことで検知します。「連続しているべきもの（時系列・連番）に穴が無いか」という観点も有効です。

```sql
-- 本来あるはずの日付（カレンダー）に対して、欠測日を洗い出す
SELECT c.d AS missing_date
FROM generate_series(
       DATE '2026-08-01', DATE '2026-08-15', INTERVAL '1 day'
     ) AS c(d)
LEFT JOIN (
  SELECT DISTINCT log_date FROM access_logs
) l ON l.log_date = c.d::date
WHERE l.log_date IS NULL;
```

## 完全性を「数値」で表す

チェックだけでなく、**継続的にモニタリングできる指標**にしておくと運用が楽になります。基本形はシンプルです。

```
完全性率（Completeness Rate） = 実際に埋まっている件数 / 埋まっているべき件数
```

- 属性レベル：`非欠損セル数 / 全行数`
- レコードレベル：`実件数 / 期待件数`
- 母集団レベル：`存在した区分数 / あるべき区分数`

これらを**カラムごと・テーブルごとに時系列で記録**しておくと、「じわじわ悪化している欠損」に気づけます。単発のチェックより、トレンドの可視化のほうが実務では効きます。

## よくある落とし穴

完全性で事故が起きるのは、たいてい「欠損の定義」か「時間軸」のどちらかです。

- **`NULL` と空文字・擬似欠損の混在**：前述のとおり。`IS NOT NULL` だけを信用しない。
- **デフォルト値による“見かけの充足”**：`0` や `1900-01-01`、`'未設定'` で埋められていると、欠損率はゼロに見えるのに中身は空。デフォルト値の存在は必ず確認する。
- **論理削除（`deleted_flag`）**：削除済み行を母数に含めると、完全性率が不当に下がる／上がる。集計の対象範囲を明示する。
- **遅延到着データ（late-arriving data）**：締め後に届くデータを「欠損」と誤検知しがち。チェックのタイミングと締めのルールを合わせる。
- **タイムゾーン境界**：日次件数が「増えた/減った」に見えるのが、実は UTC/JST の境界ずれだった、というのは定番の罠。
- **完全性と正確性の混同**：「埋まっている」ことと「正しい」ことは別。完全性はあくまで“存在するか”までしか保証しない。

## 仕組みで完全性を担保する

手作業のクエリだけでは続きません。**「入口で防ぐ」「テストで検知する」「継続監視する」** の3段構えで組み込みます。

### 1. 入口で防ぐ（制約）

そもそも欠損を入れさせないのが最も強力です。

```sql
ALTER TABLE users
  ALTER COLUMN email SET NOT NULL;

-- 「空文字も禁止」まで踏み込むなら CHECK 制約
ALTER TABLE users
  ADD CONSTRAINT chk_email_not_blank
  CHECK (TRIM(email) <> '');
```

### 2. パイプラインでテストする（dbt など）

データ基盤なら、変換パイプラインにテストを埋め込むのが定石です。dbt であれば標準のテストで属性・参照レベルの完全性を宣言的に書けます。

```yaml
# models/schema.yml
models:
  - name: orders
    columns:
      - name: order_id
        tests:
          - not_null          # 属性レベルの完全性
          - unique
      - name: customer_id
        tests:
          - not_null
          - relationships:     # 参照完全性
              to: ref('customers')
              field: customer_id
```

件数・母集団レベルは、`dbt-utils` の `recency`（鮮度）や、しきい値付きの件数テスト、あるいは Great Expectations の `expect_table_row_count_to_be_between` などで補完します。

### 3. 継続監視する

`NOT NULL` を付けられない現実のカラム（任意入力だが可能な限り埋めたい、等）は、**完全性率のダッシュボード化＋しきい値アラート**で運用します。前述の完全性率を日次でテーブルに書き出し、閾値割れで通知するのが定番構成です。

## まとめ

- 完全性は「欠損ゼロ」ではなく、「**あるべき姿に対してどれだけ揃っているか**」という相対尺度。
- **属性・レコード・データセット（母集団）** の3レベルで分けて考えると漏れが減る。
- `NULL` だけを見ない。**空文字・擬似欠損・デフォルト値**が最大の盲点。
- 事故は「欠損の定義の曖昧さ」と「時間軸（締め・遅延・TZ）」から生まれる。
- 担保は **制約（入口）／テスト（dbt等）／継続監視** の3段構えで。

次回は、完全性としばしば混同される「**正確性（Accuracy）**」を扱う予定です。
